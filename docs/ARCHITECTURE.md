# MacSync — Architettura v0.12.2 (prototipo)

## Flusso
Cartella Sorgente macOS → FSEvents → inventario e coda SQLite → worker seriale → cartella Destinazione (locale oppure SMB già montata dal Finder). Nessun componente sul server Windows 2016; macOS gestisce il login SMB esistente.

L'app permette due coppie separate di cartelle: Cartella_1 e Cartella_2. Una finestra di configurazione persistente (apribile dall'icona menu bar) offre NSOpenPanel e trascinamento Finder (UTType.fileURL), senza chiudersi quando si passa al Finder. Le coppie non devono sovrapporsi, anche tra coppie.

## Monitor e database
- Alla partenza: scansione locale della sorgente, recupero modifiche durante lo spegnimento, FSEvents dal cursore impostato prima dell'inventario iniziale.
- Durante l'attività: scansioni mirate a file o sottoalberi; query SQLite indicizzate. Nessuna scansione ricorsiva SMB ad ogni 5 minuti.
- Eventi persi, root non disponibile ed errori: interrompere i processi potenzialmente distruttivi, ritentare con scansione locale programmata.
- ChangeJournal contiene job upsert e delete: MountedFolderCopyWorker tratta gli upsert; MirrorDeletionWorker tratta i delete solamente dopo un'autorizzazione esplicita per la sessione, controlli root/volume e limiti anti-mass-delete.
- Cambio sorgente: dopo avviso esplicito, reset del solo inventario locale relativo, senza cancellare alcun file; cambio destinazione: riprepara gli upsert dei file sorgente tracciati.
- SQLite WAL in ~/Library/Application Support/MacSync/inventory.sqlite.

## Motore di trasferimento
- Controllo della disponibilità di Sorgente/Destinazione e fingerprint del volume scelto, per evitare scrittura in un mount point SMB divenuto una cartella locale.
- Validate path relativo dentro la mappatura. Rifiuta symlink come file o nelle gerarchie destinazione; niente shell né processo rclone.
- Per un singolo file (PSD/DNG/JPG ecc): copia tramite Foundation FileManager in .macsync-staging/<UUID>.partial dentro destinazione, poi verifica local file size, modification time e inode (lstat). Se stabile, sposta il temporaneo al percorso definitivo; se già esiste, utilizza replaceItemAt con backup senza cancellazione automatica. Verifica nuovamente il sorgente e solo dopo completa il job SQLite.
- Job falliti o deferred rimangono in coda, con registro dettagliato e ritentativi. In caso di errore, i file temporanei possono rimanere e devono essere puliti solo con regole di sicurezza future.
- Versione attuale: copia attivabile soltanto manualmente e per la sessione corrente. Lo spostamento può sovrascrivere un file esistente nella destinazione che l'utente ha scelto.

## Storico
SyncActivityLog crea una tabella SQLite sync_activity con timestamp, livello, root ID, azione, percorso relativo, byte, durata ed esito. Il menu bar presenta gli ultimi 200 record ed esporta fino a 5000 righe TSV; controllare i nomi file prima di condividere i log. Registro non contiene password o indirizzi IP. Future attività: filtraggio, retention/rotazione, diagnostica per codice errore.

## Anteprima di baseline
MountedBootstrapPreview esegue una scansione completa delle due cartelle selezionate solo su richiesta dell'utente e senza scrivere. BootstrapPlanner classifica i file già presenti: match presunti (size+mtime), mismatch, server-only, conflitti case insensitive. Non autorizza automaticamente il salto di trasferimenti né le cancellazioni.

## Protezioni v0.6
- Prima di ogni file copy, TransferPreflight.availableBytes legge statfs sul volume destinazione. Richiede capacità per staging + backup della vecchia versione + 16 MiB; valori non dichiarati vengono trattati come capacità sconosciuta, non come certezza di spazio.
- Dopo FileManager.copyItem verso .macsync-staging, un nuovo lstat controlla file regolare e dimensione attesa. Solo allora si procede con la verifica del sorgente e la pubblicazione. Errori rinviati lasciano job e file temporaneo; la pubblicazione su SMB deve essere ancora testata.
- StagingMaintenance.inspect conta e misura UUID.partial vecchi 7 giorni solo dentro .macsync-staging, senza ricorsione. StagingMaintenance.cleanup elimina esclusivamente elementi esplicitamente approvati dopo nuova verifica dell'ID del volume, inode, dimensione e mtime. UI blocca pulizia con copie attive e mostra conferma; niente pulizia dei backup.
- SyncActivityLog.recent supporta filtro esito e ricerca su file relativo/messaggi, export filtrato e prune del solo sync_activity (fino a 20.000 record o 90 giorni). Timer continua a lavorare ogni 5 minuti senza interrogazione ricorsiva SMB.
- Limiti non risolti: mancanza di resume byte-per-byte, hash, spazio backup illimitato, atomicità effettiva SMB, test rete/permessi reali, montaggio automatico, bootstrap e cancellazioni speculari.

## v0.7 — checksum forte dei file già seminati
- `SeededArchiveVerifier` scorre con paginazione soltanto i job `upsert` pendenti in SQLite, senza lanciare un `rclone sync` né enumerare la destinazione completa ogni cinque minuti. Per il candidato con stessa dimensione, verifica percorsi e volume, quindi legge sorgente e destinazione in streaming a blocchi di 1 MiB, calcolando SHA-256 con CryptoKit. Dimensione e timestamp da soli non provano mai l'uguaglianza.
- `SeedFileFingerprint` conserva dev/inode, size, mtime e ctime con precisione nanosecondi prima/dopo la lettura per accorgersi dei file cambiati. La GUI mostra progresso, byte letti e annullamento. Un file diverso o non disponibile resta in coda.
- `approve` è una operazione SEPARATA, approvata esplicitamente: dopo verifica delle fingerprint, `ChangeJournal.acknowledgeVerifiedFiles` esegue una sola transazione SQL con UPDATE condizionale su id/root/path/kind upsert, metadati inventario e root associata. Job rimpiazzati da FSEvents, file cambiati o cambi di root non sono marcati; DELETE mai consumati. Nessun file viene scritto o eliminato alla destinazione da questa procedura.
- La lettura SHA-256 del contenuto già presente su SMB CONSUMA comunque banda VPN, anche se evita la riscrittura. Potenziale lettura di 100 GB remoti per 100 GB già identici, oltre ai 100 GB locali. Il confronto su una cartella grande è un'operazione manuale una tantum.
- Condizione di test: GitHub Actions macOS su cartelle locali; servono prove reali di latenza/performance SMB su server Windows 2016 e iMac Sequoia prima dell'attivazione nell'archivio di produzione.

## v0.8 — modello di sicurezza cancellazioni, recupero e retention
### Autorizzazione
`MirrorDeletionPolicy` espone tre opzioni persistenti: `enabled` (default false), `recoveryEnabled` (default true), `retentionDays` (1–30 o nil=never). Le impostazioni non sono una capability: solo una sessione espressamente confermata crea `MirrorDeletionWorker`. L'avvio avviene sulla worker queue, catturando timestamp baseline, conteggio locale >0, device/inode di source e target e fingerprint del volume. Gli eventi DELETE antecedenti all'arming restano esclusi.
### Gate pre-rimozione
Prima di ogni lotto si contano TUTTI i DELETE della sessione. Con >=250 eliminazioni, o >=25 e >=10% dei file iniziali, il worker blocca il lotto. I conteggi comprendono anche le cancellazioni già completate nella sessione, per impedire aggiramenti tramite lotti piccoli in cicli differenti. Per ogni batch viene eseguita UNA scansione della sola Sorgente locale; le operazioni verificano root, volume, assenza reale sorgente anche nel caso di symlink, stato corrente in SQLite e nessun upload concorrente. Le cancellazioni su destinazione usano POSIX unlink per file regolari e rmdir solo per directory vuote; symlink e oggetti speciali non sono eliminati. La coda viene chiusa con UPDATE condizionale sul job originale.
### Recupero
Se il recupero è abilitato, invece di unlink il file target viene spostato all'interno dello stesso volume target in `.macsync-recovery/<UUID>/<percorso relativo>`: lo spostamento non ricopia i byte sulla VPN. Il manifest SQLite locale `mirror_recovery` tiene data, inode, mtime, size, durata e scadenza. `nil` significa conserva sempre. La funzione di scadenza opera soltanto quando la modalità speculare con recupero e retention finita è attiva; ricontrolla inode/mtime/size, root e volume prima di usare unlink. Non tenta cleanup su symlink, oggetti modificati o volumi sostituiti. Operazioni incompiute possono lasciare file orfani recuperabili, mai pulizia indiscriminata.
### Limiti da testare
Transazioni SQLite e filesystem non formano una transazione distribuita: un crash dopo move/unlink può lasciare il job pendente, ma non determina una seconda cancellazione arbitraria. Il recupero resta nascosto dentro target, non esiste ancora un restore guidato e può consumare spazio. I test CI coprono cartelle locali; per cancellazioni reali, ACL Windows, VPN instabile e semantica SMB sono indispensabili test su share di prova. Rinominare/spostare oggi comporta copia del nuovo file e successiva cancellazione vecchio, non moveto nativo.

## v0.9.1 — coordinatore di avvio automatico delle copie
- MacSyncRuntime è inizializzato da MacSyncApp, indipendentemente dalla finestra di configurazione, e possiede MacSyncViewModel + MountedCopyController. Il coordinatore valuta periodicamente AutomaticCopyReadiness soltanto se la checkbox di copia automatica è stata approvata. Valuta l'indice pronto, la presenza dei percorsi e il fingerprint del volume, senza tentare di montare SMB.
- Lo stato di readiness viene valutato su DispatchQueue utility, così un statfs bloccato dalla share SMB non occupa il thread della GUI. Al rientro su main actor vengono ricontrollate le condizioni di consenso, monitor, configurazione e stop prima di avviare il worker.
- MountedCopyController.startAutomaticSafeCopies crea MirrorDeletionPolicy(enabled:false,recoveryEnabled:false,retentionDays:nil) senza consultare la preferenza mirror. Il ramo manuale continua a richiedere la conferma specifica dell'utente. La modalità automatic copia/esegue update, ma non rimuove files, directory o elementi di recovery.
- La nuova VolumeFingerprint contiene anche mountSource (f_mntfromname) e viene codificata in UserDefaults al momento della selezione; la connessione è giudicata la stessa solo se filesystem/mountPath/mountSource coincidono. Profili vecchi decodificabili con mountSource nil NON sono autorizzati ad auto-copia; l'utente deve riselezionare la share nel Finder.
- Lo stop manuale mantiene una sospensione in memoria dell'auto-copy fino al successivo avvio app, per evitare riattivazioni 30 secondi dopo che l'utente ha premuto Ferma. Modifiche dei percorsi disabilitano la checkbox automatica. La ripresa di una coda al ritorno del volume è serializzata con SQLite, non con sync integrale di rete.
- Test CLI GitHub Actions macOS: automatic-readiness false/true, due destinazioni con una assente, legacy fingerprint; scenario simulato con destinazione temporaneamente cancellata e ripristinata, job conservato e DELETE intatto.
- LIMITI: Login Item SMAppService non testabile realmente su runner senza utente interattivo; nessun rimontaggio di condivisione totalmente smontata (macOS deve gestirlo), nessuna prova di velocità né autenticazione SMB reale. Non usare dati di produzione per QA.

## v0.10 — pianificazione e avviso di disconnessione
- Core SyncSchedule supporta 1–45 minuti, 1–12 ore, nextDate daily e weekly (giorno dell'anno locale, Calendario.current, DST). I valori invalidi non vengono schedulati. Data codec in UserDefaults di SyncSettingsController, default 5 minuti.
- MountedCopyController usa DispatchSourceTimer a scatto singolo con wall deadline, ripianificato sul prossimo slot della cadenza originale (evita deriva/sovrapposizioni); il primo ciclo manuale rispetta il prossimo slot configurato, quello automatico conserva lo slot assegnato dal runtime. Ogni ciclo verifica tutte le destinazioni con DestinationProbe PRIMA di qualunque azione. Se una risulta offline o diversa dal volume originale, non esegue né copie né cancellazioni e preserva la coda SQLite.
- MacSyncRuntime usa il medesimo SyncSchedule per decidere quando verificare la disponibilità delle destinazioni necessaria per armare automaticamente UPSERT. Niente controllo di connessione ogni 30 secondi. Durante una sessione attiva soltanto il worker valuta le destinazioni ai successivi slot. Il timer app/worker è operativo mentre MacSync resta avviata.
- DestinationStatusController è passive/UI-only e non fa richieste SMB: ultimo stato e lastCheckedAt arrivano dalla callback onConnectionCheck del worker o dalla verifica pre-arming allo slot automatico.
- ConnectionOutageTracker (Codable, persistito in UserDefaults) tiene firstObserved e alertSent per ID destinazione; valuta soglia di ConnectionAlertPolicy (1..168 ore, OFF default) solo per osservazioni .unavailable/.differentVolume fatte durante un tentativo di sync. Azzeramento al primo .ready. Un solo avviso per episodio; nessun timer supplementare e nessun mount SMB automatico.
- MacSyncConnectionNotifier usa UserNotifications/UNUserNotificationCenter. Il permesso viene richiesto quando viene attivata la checkbox; titolo/corpo non contengono percorsi completi, IP né segreti, nessun suono. I timer sono eseguiti nell'app, non sono scheduler di sistema capaci di riattivare un Mac spento.
- La durata disconnessione misurata parte dalla prima osservazione offline. Per sync giornaliera/settimanale, l'avviso non può comparire prima del successivo slot, anche se soglia oraria scade in precedenza. Verificare la compatibilità delle notifiche in primo piano e in background sul Mac fisico.

## MacSync v0.10.1 — correzioni di pianificazione e avvisi

- **Cadenza costante:** SyncSchedule.nextSlot usa l'ultimo slot programmato come riferimento, non la fine del trasferimento. Esempio 10:00 / 10:05 / 10:10; se il primo ciclo termina alle 10:07, lo slot 10:05 viene saltato e il nuovo ciclo è alle 10:10. Nessuna esecuzione parallela e nessuna raffica di slot arretrati.
- **Unico controllo programmato della connettività:** l'attivazione manuale e automatica non esegue probe SMB. Il runtime automatico attende il monitor locale e passa al worker lo slot originale; il worker può essere armato anche se la destinazione è offline. Solo il worker, allo slot successivo, verifica tutte le destinazioni prima di permettere operazioni. Le verifiche dell'identità del volume, delle sorgenti e dei percorsi durante la creazione delle mappature e i trasferimenti rimangono obbligatorie per sicurezza.
- **Stop:** prima di ogni nuova copia viene verificato il segnale di cancellazione; un trasferimento già iniziato può terminare. I job rimanenti restano nella coda. Le callback di una sessione fermata non aggiornano la nuova sessione.
- **Avvisi:** ConnectionOutageTracker considera inviato l'avviso solo dopo l'accettazione della richiesta da parte di UNUserNotificationCenter; se il sistema rifiuta o non è autorizzato, registra lo stato e ritenta al prossimo slot, senza timer supplementari. Le callback obsolete non possono confermare un nuovo episodio; il consenso e l'episodio vengono verificati prima della richiesta. Identificativo stabile per episodio; stato persistente. Notifica silenziosa anche in primo piano quando macOS lo consente. Disabilitando l'opzione si azzera il tracker.
- Nessuna modifica a frequenze, soglia 1–168 ore, assenza di rimontaggio automatico/credenziali/VPN gestita dall'app e conferma esplicita per le cancellazioni speculari.
- Test aggiuntivi: intervalli senza deriva o slot sovrapposti, ritardi giornalieri/settimanali, errore di invio e successivo tentativo, callback tardiva, stop della coda. Il collaudo SMB e la presentazione effettiva delle notifiche richiedono ancora un Mac fisico.

## MacSync v0.11 — resilienza e sicurezza

- Verifica di identità della sorgente per la durata della mappatura e della destinazione per la durata del singolo trasferimento. Controlli di directory, volume, symlink e percorsi riservati `.macsync-*` prima delle scritture.
- Prima della pubblicazione, verifica di snapshot del sorgente, del file temporaneo e del target originale (dimensioni, inode, device, mtime, ctime). Un target comparso o modificato durante la copia viene rinviato; la copia precedente viene preservata in un backup separato prima della sostituzione. Controllo dimensione del backup e del file pubblicato. Non è una transazione distribuita né una verifica hash completa.
- ChangeJournal.uploadIsCurrent impedisce la pubblicazione di job sostituiti da eventi più recenti durante lo staging. Se la conferma SQLite non avviene dopo la pubblicazione, il retry rilegge il job e può ripetere la copia. Temporanei e backup non vengono eliminati automaticamente in caso di guasto.
- MirrorDeletionWorker sospende le cancellazioni finché esistono upload pendenti; anche il ciclo applicativo sospende la retention in tale stato. Conserva il vecchio percorso remoto durante una rinomina se la copia del nuovo fallisce. Una coda bloccata può ritardare altre cancellazioni.
- LocalScanner distingue ENOENT dagli errori di accesso/I/O e verifica l'identità della radice prima e dopo la scansione. Una scansione fallita non modifica inventario, coda o checkpoint FSEvents.
- Test deterministici tramite fault injection locale: staging interrotto, retry con nuovo worker/connessione SQLite, modifica concorrente di sorgente e target, target comparso durante staging, root sostituita, spazio esaurito, pubblicazione senza conferma, job superato, symlink, rinomina con upload fallito e subtree inaccessibile.
- Restano necessari collaudo SMB reale e verifica con file grandi/archivio rappresentativo, atomicità e durabilità su Windows Server 2016, permessi, connessione intermittente e comportamento di macOS. I test non equivalgono a prove di crash del processo o di perdita alimentazione reali. Non utilizzare ancora dati di produzione.

## MacSync v0.12 — coda e prestazioni

- Il ciclo pianificato usa MountedFolderCopyWorker.runCycle: niente limite di 50 operazioni complessive. Acquisisce MAX(id) degli upload pendenti all'inizio; elabora pagine ordinate per ID di 100 record (limite interno configurabile nel core 1–1000). Non carica tutta la coda in memoria.
- Ogni ID viene tentato al massimo una volta per ciclo. Gli eventi nuovi, con ID superiore al limite acquisito, restano al prossimo slot; i job rimandati o falliti restano persistenti. Se la coda è vuota non accede ai singoli file. Nessun polling aggiuntivo o scansione ricorsiva della destinazione.
- Il controllo della sorgente, del volume e dei percorsi sicuri resta invariato. Un errore di volume/radice interrompe il ciclo, e una generica copyFailed verifica nuovamente la mappatura per non insistere su un volume scollegato. Stop protegge la coda; nessuna fase mirror dopo ciclo interrotto. Progress UI aggiornato a ogni pagina; una sola coda seriale, nessuna sovrapposizione fra slot.
- SQLite: nuovo indice root_id, relative_path, completed, id per verificare job ancora correnti; query con limite superiore e paginazione keyset tramite indice degli upload. Salvataggio delle impostazioni e schema precedente conservati; non si azzerano dati utente.
- Test: ampio ciclo con 235 file locali, coda sintetica da 20.000 record, eventi concorrenti, retry, interruzione/ripartenza, destinazione indisponibile e file sintetico di 64 MiB con controllo SHA-256 nel test. Non misurano banda reale o RAM durante uso SMB.
- Rinomine: rimane la procedura prudente upload prima, eventuale cancellazione dopo e solo in sessione mirror esplicitamente autorizzata. Non si interpreta una coincidenza di dimensione/data come prova di identità. Rinomina server-side e rimozione/riduzione dei backup restano da validare con SMB reale; nessuna ottimizzazione distruttiva introdotta. Nessun trasferimento di recupero parziale a offset implementato.
- Il bootstrap di archivio preseeded continua a supportare verifica SHA-256 esplicita, che legge anche i dati attraverso SMB: non dichiarare gratuito in banda. Test sintetici non dimostrano prestazioni per 100 GB, affidabilità SMB, o sicurezza di un ambiente produttivo.

## v0.12.1 — backup temporanei (punti 2 e 4 approvati)

- Mantiene copia in staging, copia separata della vecchia versione e FileManager.replaceItemAt: nessuna nuova strategia atomica o rinomina remota. Non cambia le impostazioni mirror, la cartella recupero o le coppie di cartelle.
- Il worker conferma in SQLite lo specifico job UPSERT con acknowledgeUpload: solo se il record è tuttora pendente e non superato da un evento più recente. Una conferma mancata conserva il backup.
- Solo dopo conferma riuscita tenta una pulizia puntuale del backup creato nella stessa operazione. Verifica volume, identità della radice e della directory padre, percorsi sicuri e snapshot di sorgente, pubblicazione e backup. Nessuna enumerazione della share, nessuna eliminazione ricorsiva o per pattern. Se esito dubbio, lascia il backup; un fallimento di pulizia non riaccoda una copia già confermata. Log backup_start, backup_cleanup, backup_retained con riferimento al file e al nome del backup nelle segnalazioni. Il log è soggetto alla retention ordinaria.
- Dopo crash/disconnessione, backup precedenti e residui non identificati con certezza non vengono puliti automaticamente, neanche dopo un retry riuscito. Possono richiedere manutenzione manuale. Non è un sistema di versioning, non garantisce durabilità dopo perdita di alimentazione e le verifiche correnti non sono una rilettura hash completa del file remoto. Collaudo reale SMB indispensabile per atomicità, permessi e comportamento in caso di guasto; nessuna rivendicazione di sicurezza assoluta in presenza di modifiche concorrenti tra controllo e unlink.
- Rinviata a sviluppi futuri la sostituzione con backup nativo (senza copia integrale) previa prova SMB. Nessun risparmio di traffico VPN garantito per la copia di sicurezza; riduce l'accumulo delle copie di sicurezza delle operazioni confermate.
- Punti 2/4 definiti; punto 3 ripresa parziale, punti 5/6/7 cancellazioni, punto 8 statistiche restano da concordare. Riconoscimento rinomine rinviato, nessuna correlazione tra coppie.

## v0.12.2 — ripartenza da zero e temporanei (punto 3 approvato)

- Confermato: dopo un'interruzione ripartire da zero soltanto per il singolo file non confermato; la coda SQLite resta persistente, i lavori già confermati non vengono ripetuti. Nuovo UUID staging per ogni tentativo, nessuna ripresa a offset o riuso di file parziali.
- Prima della pubblicazione, se un tentativo fallisce, verifica puntualmente la radice, il volume atteso, l'identità della cartella staging e il temporaneo del tentativo corrente (percorso UUID inizialmente assente, tipo file, snapshot invariato durante il controllo). Verifica anche che il sorgente sia ancora disponibile e invariato. Solo se tutti i controlli riescono elimina il temporaneo tramite unlink, senza toccare foto definitive, backup o altri temporanei. Nessuna scansione aggiuntiva SMB.
- Se la connessione è realmente assente, il sorgente cambia, le identità non corrispondono, o è già stata tentata la pubblicazione, conserva eventuali residui e registra staging_retained; non tenta pulizia indiscriminata dopo il riavvio.
